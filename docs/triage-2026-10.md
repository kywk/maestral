## Recommended shortlist (priority order)

### P1 — #925 / #926: zero-byte files on Dropbox after transport retries

- Links: [#925](https://github.com/samschott/maestral/issues/925),
  [#926](https://github.com/samschott/maestral/issues/926); related
  [#1080](https://github.com/samschott/maestral/issues/1080) (same era, initial-sync
  conflicts + zeroing).
- Symptom & impact: files with local content become **0 B on Dropbox**; user-visible
  as corrupted/blank documents (Scrivener bundles, 1Password vaults) and files lost
  locally on the next remote pull. #926 additionally reports periodic full re-uploads.
  Data-loss class, the worst failure mode a sync client can have.
- Who's affected: macOS users uploading many small files / large folder trees that hit
  transient transport errors.
- Reproducibility: **medium — and not fully closed.** Upstream v1.8.0 changelog: "data
  transport errors that are retried could result in zero byte files being created in
  the cloud if the local file size is smaller than 4 MB". A reporter in #925 still saw
  it on 1.9.4 (2024-07) with debug logs; upstream never confirmed a residual cause.
  Exact trigger for the residual cases is unconfirmed.
- Suspected code: `src/maestral/client.py` — `DropboxClient._upload_helper()`,
  `upload()`, `_upload_session_*` helpers, `_retry_on_error(DataCorruptionError,
  MAX_TRANSFER_RETRIES)`; error conversion in `src/maestral/errorhandling.py`.
- Rough fix approach: add a **post-upload invariant**: after `files_upload*` returns,
  compare the returned metadata `size` (and `content_hash` when available) with what
  was actually read from disk; on mismatch raise `DataCorruptionError` so the existing
  retry loop re-reads and re-uploads, and log path/size/request-id at ERROR. This is
  cheap, testable offline (`tests/offline/test_client.py` already mocks the SDK) and
  converts a silent data-loss into a retried error.
- Effort: **M** (verify hashing assumptions, add tests, run on a large tree).
- Risk: low-to-medium — touches the upload hot path, but only adds a check and reuses
  the existing retry path. Residual root cause may remain if the corruption happens
  server-side after a successful response.
- Rank rationale: highest blast radius and only data-loss issue in the list; worth
  hardening even without a confirmed repro.

### P2 — #1116: sync stuck after deletions in a shared folder (verify; hardening)

- Link: [#1116](https://github.com/samschott/maestral/issues/1116) (macOS 15.5, 1.9.4).
- Symptom & impact: files deleted remotely by another user in a shared folder leave
  sync stuck at 0%; uploading stops until restart. Silent sync failure.
- Reproducibility: user gives concrete steps (upload, other user deletes); no logs.
  **Likely — but not confirmed — already fixed by this fork**: the fork's delete fix
  (`2aeae2ba`) covers exactly "remote deletions affecting local items whose paths only
  differ in case", where a verification failure raised `FileNotFoundError` out of
  `SyncEngine._on_remote_deleted`, killed the download cycle, and (because the cursor
  only commits after a full cycle) crash-looped on every resume. A shared folder with
  mixed-case renames is a plausible source of such paths.
- Suspected code: `src/maestral/sync.py` `_on_remote_deleted()` (~line 3689,
  `delete(..., force_case_sensitive=...)`), `src/maestral/utils/path.py` `delete()` /
  `to_existing_unnormalized_path()`.
- Rough fix approach: (1) check daemon logs for `FileNotFoundError`/`ENOTDIR`/`ELOOP`
  before the fork's deploy date to confirm the mechanism; (2) extend the new regression
  tests (`tests/offline/utils/test_path.py`, 66a4505f) with a directory-level case:
  remote dir deletion where a child is a symlink or the local path is a regular file in
  a folder position; (3) audit the other `_on_remote_*` handlers for exceptions
  escaping into `manager._handle_sync_thread_errors` and pausing sync (the same
  pattern: helpers that may raise where the caller only handles returned errors).
- Effort: **S** (verification + tests, no production change expected).
- Risk: minimal; test-only unless the audit finds another leak.
- Rank rationale: cheapest item with real payoff — confirms a shipped fix and closes
  the gap that a *different* unguarded raise in the download path could still cause.

### P3 — #1085: macOS downloads keep NFC names instead of NFD

- Link: [#1085](https://github.com/samschott/maestral/issues/1085); related stale
  #410 (Cyrillic/Greek uppercase path handling, same `path.py` area).
- Symptom & impact: Maestral writes composed (NFC) filenames on macOS; the official
  Dropbox client writes decomposed (NFD) names (APFS preserves whichever form the app
  writes). Consequences: names differ from what macOS tooling and the official client
  produce, duplicate-looking entries after client switches, mismatch with Dropbox web
  and other machines; Finder/Spotlight UX oddities. Not data loss, but a permanent
  fidelity gap on the fork's primary platform.
- Who's affected: macOS users syncing names with accents/Hangul/other composable
  characters, especially shared folders also touched by Dropbox web or non-Mac clients.
- Reproducibility: **high** — create `café.txt` on a Linux client (NFD on disk via
  `touch $'cafe\u0301.txt'`) or upload via Dropbox web, then sync on macOS and inspect
  `ls | xxd`.
- Suspected code: `src/maestral/utils/path.py` — `normalize_unicode()` (unconditional
  `unicodedata.normalize("NFC", ...)`), used by `normalize()`; local path construction
  via `to_local_path()` / `to_local_path_from_cased()`; upload side `to_dbx_path()`.
- Rough fix approach: keep the DB/index keys on NFC (`normalize()` is the cross-platform
  equivalence function — don't change it, or existing indexes re-conflict), but
  translate **at the local-path boundary**: on Darwin, create/rename local entries with
  `unicodedata.normalize("NFD", name)` and convert NFD→NFC when building dbx paths.
  `equal_but_for_unicode_norm()` already exists and is the right comparison for
  renames that only change normalization. Add Darwin-gated unit tests; consider a
  one-time migration for already-NFC local names (rename pass) or document `rebuild-index`.
- Effort: **M**.
- Risk: medium — path handling is load-bearing (case-sensitive deletes, renames,
  conflict resolution); needs macOS + Linux test runs. Keep the change behind one
  helper, not scattered.
- Rank rationale: best ratio of user-visible correctness to effort among the
  platform-specific issues; squarely in the fork's macOS focus.

### P4 — #999: `.mignore` upload error on read-only roots (business accounts)

- Link: [#999](https://github.com/samschott/maestral/issues/999); related confusion in
  [#1106](https://github.com/samschott/maestral/issues/1106) (documentation: `.mignore`
  filters local/upload events only — downloads are selective sync's job, see
  `docs/background/sync_logic.rst`).
- Symptom & impact: on Dropbox Business accounts the root is not writable; Maestral
  keeps trying to upload `<root>/.mignore` and reports `InsufficientPermissionsError`
  ("Could not sync .mignore") every cycle, i.e. permanent sync-issue state and, with
  `notification_level <= SYNCISSUE`, a repeated notification each cycle (on Linux;
  on macOS the daemon's notifications are dropped today, see `docs/gui-plan.md`).
- Who's affected: business/team accounts with read-only roots; only users who place a
  `.mignore` at the root (as documented).
- Reproducibility: reporter-verified; easy to simulate by making the root read-only or
  by pointing a test account at a team-space root. **Medium confidence** without a
  business account.
- Suspected code: `src/maestral/sync.py` `is_mignore()` / `_is_mignore_path()` and the
  local-event filter in `list_local_changes()` (~line 1932); `constants.py`
  `EXCLUDED_FILE_NAMES` (does not contain `.mignore`); sync-issue plumbing in
  `manager.py`.
- Rough fix approach: treat the mignore file as **local-only config**: filter its own
  local events (created/modified/moved) before they reach `apply_local_changes`, while
  still watching it (the manager already calls `sync.load_mignore_file()` on changes).
  Optional secondary improvement: log a one-time warning when a `.mignore` rule matched
  nothing during a scan, which would have answered #1106 directly.
- Effort: **S**.
- Risk: low — if a user *does* want `.mignore` propagated through Dropbox, they lose
  that (undocumented) behaviour; note it in the changelog.
- Rank rationale: small, self-contained, removes a permanent error state for a class of
  accounts; doubles as `.mignore` documentation cleanup.

### P5 — #964: `KeyError: 'error'` in the Dropbox SDK crashes a sync cycle

- Link: [#964](https://github.com/samschott/maestral/issues/964); same traceback as
  closed [#961](https://github.com/samschott/maestral/issues/961), where upstream
  diagnosed 429 rate-limit responses lacking the `error` field and Dropbox later fixed
  the format server-side.
- Symptom & impact: an unusual API response raises `KeyError` from
  `dropbox_client.raise_dropbox_error_for_resp()` inside the SDK; it escapes the client
  layer, trips `manager._handle_sync_thread_errors`, pauses sync and shows "Unexpected
  error" — any future API format/proxy/edge response repeats the pattern.
- Who's affected: rare/unknown (server-side root cause reportedly gone); #1105 shows the
  same crash class can come from local environment changes (proxy var, Python upgrade).
- Reproducibility: **low** — cannot be triggered on demand; fix is defensive.
- Suspected code: `src/maestral/client.py` `_DropboxSDK.request_json_string()` override
  and its `super()` delegation; conversion helpers in `src/maestral/errorhandling.py`.
- Rough fix approach: wrap the SDK call path so `KeyError` (or a non-JSON body) becomes
  a retriable `NetworkError`/`MaestralApiError` with the request id and status code in
  the message, instead of a bare crash; add an offline unit test with a malformed SDK
  response.
- Effort: **S**.
- Risk: low.
- Rank rationale: cheap hardening of a crash class, but lower priority than P1–P4
  because the known trigger is already gone and it needs the client-layer retry
  semantics to stay correct.

## Already addressed / likely fixed by this fork (do not re-fix)

- **Case-sensitive delete crash loop** (`2aeae2ba`, v1.10.0): likely closes **#1116** —
  see P2. Any future report of "sync stuck after remote deletes / paused forever" should
  first be checked against this fix and the new tests in
  `tests/offline/utils/test_path.py`.
- **Watchdog-6 companion modified events for recursive ignores** (`08b317a8`, v1.10.0):
  content under a newly created, recursively ignored folder no longer leaks modified
  events into the upload queue. No single open upstream issue maps 1:1 to this (it was
  found in fork testing); the closest user-visible themes are `.mignore`/excluded-item
  confusion (#446, #1106) — those are separate and not closed by it.
- v1.10.0 also pins `dropbox>=11.28,<12.1` (SDK internals used by the streamed-upload
  override). **Do not unpin** while working on P1: the pin exists precisely because
  the upload path depends on SDK internals.

## Out of scope for now (and why)

- **Windows support (#66) and WSL oddities (#132)** — no Windows machine in the loop;
  the fork is macOS/Linux.
- **Linux Qt GUI / PyQt6 / packaging (#355, #356, #657, #689, #729, #837, #1088,
  #1094)** — the maintainer runs the daemon via launchd CLI on macOS; GUI work on Linux
  has no consumer here.
- **GUI features and the frozen macOS app** (#354, #590, #598, #956, #986, #1098, #1100,
  #1127, #1147) — the GUI is the frozen upstream 1.9.5 bundle; see
  `docs/gui-plan.md`. Menu-bar icon/notification complaints cannot be fixed without
  rebuilding the app.
- **Selective sync 2.0 / Smart Sync / Dropbox Transfer (#462, #677, #743, #828, #865)**
  — large feature work on an archived codebase; not required for personal use.
- **Other backends / platform expansion (#177 encryption, #1042 S3, #1102 Android,
  #593 Google Drive, #38 OpenBSD)** — no personal need, unbounded maintenance.
- **Multiple accounts in one instance (#851), post-sync hooks (#835), size limits
  (#1000), Finder integrations (#334, #568, #580)** — features; revisit only if daily
  usage demands them.
- **Indexing/CPU/memory investigations (#390, #491, #497, #998, #1016)** — real but
  expensive to profile and not reproducible on the maintainer's setup; watch-only.
- **Sleep/display-disconnect daemon stop (#1101)** — actionable only with reproduction
  logs around wake events; the fork's launchd agent + `maestral-healthcheck` covers the
  "daemon not running" symptom operationally.
- **Conflict-copy pile-ups with the official client on other machines (#910, #1079,
  #1080)** — multi-client semantics, no reliable repro; revisit if they appear locally.
